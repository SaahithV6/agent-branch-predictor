# Rank candidates, don't generate calls: building a CPU tool predictor

The best architecture for this job is a **two-stage, CPU-only learned predictor**. Stage one picks the next tool with an n-gram/Markov table or a small gradient-boosted (GBDT) classifier over the last few call signatures. Stage two fills arguments with a **LightGBM pointer-ranker** that scores every scalar leaf in the recent tool results (and spans of the user text) as a candidate for each argument slot. The output passes through a **calibrated abstention gate**: isotonic scores plus a Learn-then-Test or Wilson upper-bound threshold set per domain and per (tool, arg) slot. This design generalizes the current rule table instead of replacing it: "this field path fed this argument before" becomes one feature among many, and schema-agnostic features (key-name similarity, type, recency, value rarity) carry patterns over to tools the table has never seen. The case rests on three findings. First, every LLM-drafter system in the 2024-2026 literature lands at **13-66% exact next-call accuracy at 1.7-3 s per prediction**. Second, the closest published analogue, PASTE, already shows that mined patterns plus deterministic argument mappers run in **under 100 ms** and cut end-to-end latency **43.5%**. Third, arguments, not tool names, are where every method loses accuracy. Small function-calling LMs belong in the system as offline teachers and as an asynchronous fallback, never on the hot path. No published work evaluates a GBDT ranker on agent traces, so this recommendation fills an open niche: it is an engineering inference from adjacent evidence, and the evaluation protocol below is built to falsify it.

## The rule table already beats every published LLM drafter

The bar any new model has to clear is high. In this repo's own live tau-bench retail run (Claude Haiku 4.5, nested 5-fold CV over test-task customers), strict mode guessed **98% of predicted reads correctly at 47% coverage**, and text mode reached **84% at 64%**. Injected end to end, it cut the agent's tool calls **47%** and model turns **42%** with no loss in write-action correctness ([README](/home/lain_iwakura/Documents/agent-branch-predictor/README.md)). The weakness is the airline replay: a loose text rule that looked fine on 30 tuning tasks fired **125 wrong guesses on 20 holdout tasks** ([README](/home/lain_iwakura/Documents/agent-branch-predictor/README.md)). That failure, and the inability to cover tools without hand-mined rules, is what a learned model must fix.

Published LLM speculators sit far below this line. Speculative Actions predicts **22-38% of tau-bench retail API calls** correctly using gpt-5-family and Gemini-Flash speculators at ~2-3 s each ([Speculative Actions](https://arxiv.org/html/2510.04371v1)). Speculate with Memory adds a transition table, embedding-retrieved episodes, and a confusion tracker to a GPT-4.1-mini speculator. That lifts tau2-bench read-only full-match accuracy from only **12.7% to 19.9%**. Its live HotpotQA run reached a 40% hit rate but just a **1.05x speedup**, because the speculator's 1.7 s median latency ate the window it was meant to fill ([Speculate with Memory](https://arxiv.org/pdf/2607.12236)). Self-speculation does better because the agent predicts itself. Joint RL lifts a Qwen3-4B agent's Hit@1 from 44.1 to 61.2 ([Speculate While You Reason](https://arxiv.org/abs/2607.25816)), and SPORK reaches 0.792 exact-argument agreement on tau2 ([SPORK](https://arxiv.org/pdf/2607.03333)). Both need ownership of the serving engine (KV-cache forking, logprobs), so neither applies to a hosted Haiku or Claude agent.

The decisive pattern is where the errors land. SPORK's probe names the right tool **74.6-99.6%** of the time at decode start, yet gets arguments exactly right only **7.6-83.9%** of the time ([SPORK](https://arxiv.org/pdf/2607.03333)). Even LLaMA3.1-405B reaches a **14.7% tree pass rate** on NesTools' nested parameter filling, where later calls consume earlier responses ([NesTools](https://arxiv.org/abs/2410.11805)). Sequence-only next-activity models reach roughly **80% accuracy** on process logs ([EmergentMind summary of ProcessTransformer](https://api.emergentmind.com/topics/processtransformer)), and on low-entropy logs a Random Forest nearly ties transformers ([DAW-Transformer](https://www.arxiv.org/abs/2502.10573)). Tool choice is the easy half. Binding a value from a prior JSON result to the next call is the hard half, and it is a retrieval problem, not a generation problem. PASTE's motivating statistic makes the point: in **95% of web visits the URL is a strict substring of the preceding search output** ([PASTE](https://arxiv.org/html/2603.18897v3)).

## Five architectures ranked by precision per CPU millisecond

The table ranks the options for the stated constraints: trains on traces, generalizes across domains, low CPU latency, high precision. Latencies are order-of-magnitude estimates from the research notes, not measurements, and LightGBM ranking cost at this candidate scale still needs a local benchmark.

| Rank | Architecture | Role | Est. CPU latency | Cross-domain | Calibratable | Evidence |
|---|---|---|---|---|---|---|
| 1 | n-gram/GBDT next-tool + **LightGBM pointer-ranker** over result leaves + LTT/Wilson gate | Hot-path predictor | ~0.1-2 ms | Good if features are schema-agnostic | Yes (isotonic + LTT) | Generalizes PASTE mappers ([PASTE](https://arxiv.org/html/2603.18897v3)); no direct published test |
| 2 | Same, plus kNN episodic retrieval over embedded context | Adds context conditioning | +<50 ms embedding lookup | Good | Yes | Memory gave +19-39% relative ([Speculate with Memory](https://arxiv.org/pdf/2607.12236)) |
| 3 | Tiny transformer/LSTM encoder + pointer head (ONNX) | Upgrade once GBDT plateaus and >~10^5 labeled events exist | ~1-10 ms | Moderate | Needs post-hoc calibration | Pointer Networks ([arXiv](https://arxiv.org/abs/1506.03134)), TRADE copy slots ([arXiv](https://arxiv.org/abs/1905.08743)) |
| 4 | Small function-calling LM (xLAM-1b, Hammer-1.5B, Qwen2.5-0.5B) | Offline teacher/labeler; async fallback on abstain | ~0.5-3 s | Best zero-shot | Weak (token logprobs) | TinyAgent-1.1B ~2.9 s on device ([arXiv](https://arxiv.org/abs/2409.00608)); xLAM-1b 78.94% BFCL ([HF](https://huggingface.co/Salesforce/xLAM-1b-fc-r-gguf)) |
| 5 | GNN over tool/result graph | Feature source only | ~1-10 ms | Speculative | Needs calibration | Helps task-graph planning ([GNN4TaskPlan](https://arxiv.org/abs/2405.19119)); no published use for argument binding |

The top choice wins because it matches the shape of the problem. Pointer Networks set the output vocabulary equal to the input positions ([Pointer Networks](https://arxiv.org/abs/1506.03134)), which is exactly "choose a field from a prior result". Replacing the softmax with an independent per-candidate GBDT classifier keeps that framing, adds cheap calibration, runs in microseconds per candidate, and accepts hand-engineered features that transfer across schemas. Generative copy models such as CopyNet and pointer-generator ([CopyNet](https://arxiv.org/abs/1603.06393), [See et al.](https://arxiv.org/abs/1704.04368)) earn their cost only when an argument is a *transformation* of prior values (concatenation, reformatting) or comes from free text. Verbatim ID copying, which dominates tau-style and CRM-style traces, does not need them.

The repo already has evidence for rank 4's role. Haiku used zero-shot as a predictor reached **92-97% precision at 67-70% coverage**, but at **2.5-3 s**, while a distilled TF-IDF + logistic-regression classifier reached **82% precision at 93% coverage** with no history ([README](/home/lain_iwakura/Documents/agent-branch-predictor/README.md)). A large model produces good labels and a small learned model inherits much of that skill at CPU cost, which is the distillation path this report recommends. The same README warns that on ad-hoc Claude Code transcripts the exact next call is predictable only **~2%** of the time. Open-ended coding sessions are not a target domain for any architecture here.

Graph structure should enter as features: the copy frequency on (tool, arg) <- (tool, result path) edges, and 2-hop "value flowed A->B->C" chains. Graph-based models in process mining roughly tie LSTMs ([arXiv 2507.15411](https://arxiv.org/pdf/2507.15411)), so message passing at inference buys nothing proven for exact-match copying.

## Calibrated abstention sets the precision/coverage curve

Treat this as selective classification. Choose the confidence threshold that guarantees a target risk with high probability while maximizing coverage ([Geifman and El-Yaniv](https://arxiv.org/abs/1705.08500)). Precision is not monotone in the cutoff, so standard conformal methods do not control it directly. Learn-then-Test does: scan thresholds and keep those whose upper confidence bound on error stays below alpha, with a 1-delta guarantee under i.i.d. data ([conformal tutorial](https://arxiv.org/abs/2107.07511), [LTT](https://arxiv.org/abs/2110.01052)). Naive thresholds measurably undershoot. In MAPIE's precision-control demo, the raw calibration threshold delivered **0.763 test precision** below target, while risk control delivered **0.855** ([MAPIE](https://mapie.readthedocs.io/en/stable/_sources/examples_risk_control/1-quickstart/plot_risk_control_binary_classification.rst.txt)).

The gate should work at two levels. Globally, isotonic-calibrated ranker scores face a single LTT threshold at the target precision (95% for prefetch, higher for inject mode, where a wrong result enters the model's context). Per (tool, arg) slot, a slot may fire only once its Wilson lower bound on held-out precision clears the target with a minimum count of positives. That rule directly blocks the airline failure, where a pattern with too few samples fired 125 wrong guesses. The margin between the top-1 and top-2 candidate scores, the ambiguity count (how many leaves hold the same value), and value rarity belong in the ranker as features. They are the inputs that let it abstain when two order IDs are equally plausible. Spurious matches on low-entropy values such as "1", "true", or short codes are the biggest single risk to the auto-labeling.

Expected tradeoffs follow from the baseline and the literature. No paper reports a precision/coverage curve for tool-call speculation, so these are hypotheses to test, not results. At matched precision (98% strict), a ranker should add coverage mainly where rules are sparse: unseen tools, rare paths, and indexed list selections, which PASTE handles with "indexed selection with fallback" mappers ([PASTE](https://arxiv.org/html/2603.18897v3)). The realistic goal is to **beat 47% coverage at 98% precision on retail and to avoid ever firing below target on airline**. On airline, abstaining is the win. Multi-candidate speculation trades precision for hit rate: PASTE's top-1 accuracy is only **27.8%**, its top-3 recall **43.9%**, and its any-candidate hit rate up to **93.8%** ([PASTE](https://arxiv.org/html/2603.18897v1)). For speculate mode, where a miss costs only a wasted read, issuing the top-k above a lower threshold is rational. For inject mode, only top-1 above the strict threshold should fire.

The firing rule should also weigh value, not just confidence. Speculate call c when **P(hit) · L_tool(c) > lambda · Cost(c)**, with L_tool taken from production span durations. Speculative Actions shows that confidence-aware launching reduces to a constant threshold under stationarity, and that one-step breadth speculation caps the latency reduction at **50%** ([Speculative Actions](https://arxiv.org/html/2510.04371v2)). Tool execution makes up **35-61%** of request time in PASTE's workloads, and calls whose arguments come from prior outputs tend to be the slow ones ([PASTE](https://arxiv.org/html/2603.18897v1)), which is exactly the class the ranker targets.

## Train on tau2's S3 dump, split by task and user, hold out a domain

The largest ready-made training corpus is the tau2 leaderboard bucket. It is anonymously listable, holds about **92 submission folders** of multi-model, 4-trial trajectories across airline, retail, and telecom, and stores tool-call arguments, JSON results, and per-message timestamps ([leaderboard docs](https://github.com/sierra-research/tau2-bench/blob/main/docs/leaderboard-submission.md), [bucket listing](https://sierra-tau-bench-public.s3.amazonaws.com/?list-type=2&prefix=submissions/&delimiter=/)). tau2 also tags each tool READ or WRITE: retail has 7 READ and 7 WRITE ([retail tools.py](https://github.com/sierra-research/tau2-bench/blob/main/src/tau2/domains/retail/tools.py)). Those tags are free safe-to-speculate labels. One caveat overrides everything: tau tool messages arrive **~0.2-0.3 ms** after the call, while LLM turns take 5-9 s ([S3 trajectory](https://sierra-tau-bench-public.s3.amazonaws.com/submissions/claude-3-7-sonnet_anthropic_2024-06-20/trajectories/claude-3-7-sonnet-20250219_airline_default_gpt-4.1-2025-04-14_4trials.json)). On tau, prefetching saves only turns and tokens, never tool wall time, unless latency is injected from production spans. The repo's real-workflow test confirms this: 95% precision but no speedup, because the tools take 5-12 ms ([README](/home/lain_iwakura/Documents/agent-branch-predictor/README.md)).

xlam-function-calling-60k stores no results, so it cannot teach argument copying ([HF](https://huggingface.co/datasets/Salesforce/xlam-function-calling-60k)). Label quality also has a ceiling. SABER found annotation errors cap retail at ~92% and airline at ~70% ([SABER](https://arxiv.org/html/2512.07850v1)), and one audit found the user simulator went off-instruction in **22%** of airline conversations ([AURA](https://arxiv.org/pdf/2505.01592)).

The evaluation protocol has to rule out the leak that killed the earlier train-only result (5% coverage, because train requests quote the order number and test requests do not). Split on tau2 `split_tasks.json` task IDs ([tau2 domains](https://github.com/sierra-research/tau2-bench/tree/main/data/tau2/domains)), never on trajectories, and also hold out users and entities. For cross-domain claims, run **leave-one-domain-out** (train retail+airline, test telecom) and exclude APIGen-MT whenever testing on tau. For each tool-call opportunity, report Hit@1 exact match on name plus the full argument dict, as Speculate While You Reason defines it ([arXiv](https://arxiv.org/html/2607.25816v1)). Report it next to name-only accuracy and argument-key F1, so tool selection and argument filling can be diagnosed separately. Also report top-k recall, coverage, and wasted speculative calls per task. End to end, report mean and p95 latency, input tokens, and task success with **pass^k** ([tau-bench](https://arxiv.org/html/2406.12045)) using paired seeds against a non-speculative arm, with one fixed user simulator per tau2 leaderboard rules. If the predictor learns online, fix how much history it has seen: Speculate with Memory's latency gain grew from ~28% to over 50% on ALFWorld as experience accumulated ([arXiv](https://arxiv.org/pdf/2607.12236)). Every number should be reported at matched precision against the rule table's 98%/47%, not as a free-floating accuracy.

## Implementation: one record schema, auto-labels, deny-by-default

Normalize every source into one row per tool call: trace/session id, span id, parent, tool name, call id, args JSON, result JSON, start and end timestamps, error, and user/tenant id. That schema maps onto OTel `execute_tool` spans (whose arguments and results are opt-in attributes) ([OTel](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md)), OpenInference TOOL spans ([OpenInference](https://arize-ai.github.io/openinference/spec/semantic_conventions.html)), LangSmith runs ([LangSmith](https://docs.langchain.com/langsmith/run-data-format)), and Langfuse tool observations ([Langfuse](https://langfuse.com/docs/observability/data-model)). The Langfuse `user_id` and OTel `gen_ai.conversation.id` fields make held-out-user splits possible on production data.

Labels come free from the traces. For each real call (B, args), flatten every prior result in the session to (call index, JSON path, value) leaves and add n-gram spans from the user text. A leaf is positive for slot (B, X) when its normalized value equals the argument actually used, and every other leaf is negative. Drop or downweight positives whose value is low-entropy or appears at many paths. Speculate with Memory's `arg_sources` uses the same provenance trick, substring-matching argument values against prior observations ([arXiv](https://arxiv.org/pdf/2607.12236)). The repo's own value-flow mining, which already derives the rule table, is the right place to emit these rows instead of building a second labeler.

Ranker features fall into four groups. Schema features cover arg-name vs. leaf-key token overlap, type match, and format regex (ID-like, email, date). Position features cover recency in calls back, list index, and depth. History features cover the rule table's Wilson score for this (path -> arg) edge, the edge count, and whether the value was already used. Ambiguity features cover sibling candidates with the same value, value rarity, and the top-1/top-2 margin. The next-tool stage starts as an n-gram over the last k (tool, outcome) signatures and graduates to a GBDT only if it measurably helps. A Markov baseline is mandatory, because simple models tie transformers on low-entropy logs ([DAW-Transformer](https://www.arxiv.org/abs/2502.10573)), and customer-service traces are low-entropy. Distill into this stack from a large model: run Haiku or a fine-tuned xLAM/Hammer offline over traces to propose labels for rare tools, then train the GBDT on them. Keep the small LM as an asynchronous fallback only where the speculation window exceeds ~3 s. Hammer's "function masking" exists to make models robust to tool and parameter renaming ([Hammer](https://arxiv.org/abs/2410.04587)), which is the cross-domain property the schema features try to capture cheaply.

Safety is deny-by-default and never inferred. PASTE defaults to `allow: false` and "does not infer side-effect freedom automatically" ([PASTE](https://arxiv.org/html/2603.18897v1)). Use tau2 READ tags or `readOnlyHint: true` from **trusted** servers only, because MCP states clients should never make tool-use decisions from annotations sent by untrusted servers ([MCP schema](https://modelcontextprotocol.io/specification/2025-06-18/schema)). Exclude billed or rate-limited open-world reads, invalidate cached results on any write (the repo already clears its cache on writes), and audit discarded speculative reads, which can leak intent at issue time ([Ghost Tool Calls](https://arxiv.org/pdf/2606.02483)). Ship every new domain in `PREDICTOR=shadow` first. Promote it to `speculate`, and later to `inject`, only once live shadow precision clears the slot-level Wilson bound, because the i.i.d. assumption behind LTT breaks under tenant and domain shift.

## Conclusion

The literature's drift toward bigger and more self-aware speculators (memory-augmented drafters, RL-trained self-speculation, KV-cache forking) solves a problem this system mostly does not have. For hosted agents whose tool arguments are copied IDs, prediction is a retrieval-and-calibration problem. The gains come from deciding *when not to fire* and from features that make a never-seen schema look familiar, not from a model that writes JSON. The real open question is cross-domain transfer. No source tests whether name, type, and recency features alone can carry a copy pattern into a new tool family, so the first experiment to run is leave-one-domain-out on the tau2 dump at a fixed 98% precision target.

The second implication is about measurement. tau benchmarks have zero tool latency, so every tau "speedup" from prefetching is really a turn- and token-reduction effect. That favors inject over speculate, and it means production span durations, not benchmark wins, should decide which tools are worth predicting at all. A ranker that adds 10 points of coverage on 5 ms tools is worth less than one that adds 3 points on 2 s tools, and the P(hit) · L_tool firing rule makes that tradeoff explicit.
